# 서울 커피 상권 분석 컨설팅

PE가 보유한 커피 전문점 체인(클라이언트 기본값: 프랜차이즈 본사)의 신규 출점 전략을 만든다. 질문은 하나다. **"3년 뒤 성장할 서울 커피 상권은 어디이고, 거기에 어떤 매장을 내야 하는가."** 베이커리는 범위 밖이다.

평가자(퍼플)를 설득하는 힘은 **데이터 정합성과 데이터 활용 방법**에서 나온다. 화려한 디자인보다 "이 숫자는 어디서, 언제, 어떤 단위로 왔고, 한계는 무엇이며 어떻게 보정했는가"에 답하는 것이 먼저다. 모든 단계는 이 기준으로 판단한다.

## 역할 (Role)

12개 에이전트는 분리해서 띄운다. 한 에이전트가 여러 역할을 겸하면 검토가 자기 확인이 되어 평가가 의미를 잃는다. 각 역할의 정체성·입력·출력·말투는 `references/agents.md`에 있다. 서브에이전트를 띄울 때 해당 절을 프롬프트에 그대로 넣는다.

| 에이전트 | 한 줄 역할 | 산출물 |
|---|---|---|
| 블랙 | 총괄·결정권자. 톤앤매너·스토리라인 통일, 재작업 범위 결정 | `black_review.md`, `iteration_log.md` |
| 레드 | 리서처. API 데이터 전량 수집·품질 기록 | `data/*.csv`, `data_quality.md` |
| 블루 | 분석가. 가설 수립·검증·베스트 프랙티스 | `hypotheses.md` |
| 그린 | 검증자. 가드레일·병목·오류 도출, 원본 대조 | `risks.md` |
| 브라운 | 해결사. 그린의 문제를 데이터로 해결 | `solutions.md` |
| 실버 | 자문. 블랙과 함께 베스트 솔루션 1개로 수렴 | `final_solution.md` |
| 옐로우 | 디자이너. Material Design 3 시안 | `design_spec.md` |
| 오렌지 | HTML 개발자. 최종 보고서 | `output/report.html` |
| 화이트 | 영상 개발자. 30초 소개 영상 | `output/video/` |
| 퍼플1·2·3 | 독립 평가자. 10점 만점 채점 | `scores_<회차>.json` |

## 평가 기준 (Rubric)

5개 항목(정교성·정합성·설득력·실행 시사점·전달력)을 퍼플 3명이 각자 10점 만점으로 채점한다. **통과 = 퍼플 1·2·3 모두, 모든 항목에서 9.5점 이상** (평균이 아니라 최저점 기준). 항목 정의와 점수대별 기준, 데이터 정합성 가중 관점은 `references/rubric.md`.

## 맥락 (Context)

- 케이스 브리프와 목차: 입지 선정 → 인테리어 컨셉 → 메뉴 구성 → 손익 시뮬레이션. 산출물은 HTML 1장 + 30초 영상, 발표는 3분·결론 우선(Answer First).
- 데이터: 서울 열린데이터광장 상권분석서비스. 서비스명·필드·단위·한계는 `references/data-sources.md`.
- 퍼플1 페르소나: `references/persona_purple1_seed.md`에서 시작해 공개 자료로 보강한다.
- 디자인 토큰: `references/design-tokens.md` (옐로우·오렌지·화이트 공통).

## 도구 (Tools)

- `seoul-opendata` MCP (`search_datasets`, `get_data`): 데이터셋 탐색과 개별 확인.
- `scripts/fetch_district.py <프로젝트폴더> --quarters 8`: 레드의 대량 수집. 원본을 `raw/`에 그대로 두고, 커피-음료만 `data/*.csv`(행마다 `_source`, `_called`)와 `data/manifest.json`으로 뽑는다. API를 손으로 페이지 넘기며 부르지 말고 이 스크립트를 쓴다. 페이지가 수백 개라 손으로 하면 누락이 생기고, 누락은 곧 정합성 감점이다.
- `scripts/gate_check.py <프로젝트폴더>`: 블랙의 퍼플 평가 전 게이트(키 노출, 차트 출처 캡션, 필수 섹션·산출물).
- Workflow 도구(다이나믹 워크플로우)로 에이전트를 오케스트레이션한다. 스크립트를 쓰기 전에 `workflow-authoring` 스킬을 불러 API를 확인한다.
- 웹 검색: 퍼플1 페르소나 보강, 임대료·원가 같은 API에 없는 보조 근거(출처 필수)에만 쓴다.

## 진행 규칙 (Workflow)

프로젝트 폴더 기본값은 `<작업폴더>/output/` 의 상위(작업폴더 자체)이고, 최종 산출물은 `<작업폴더>/output/`에 둔다. 시작할 때 사용자에게 한 줄로 확인한다: 클라이언트(기본 프랜차이즈 본사), Top N(기본 5), 영상 형식(기본 HTML/CSS 30초 애니메이션, ffmpeg가 있으면 MP4도).

워크플로우 한 회차:

1. **레드** — `fetch_district.py`로 최근 8개 분기 수집 → `data_quality.md`(데이터셋별 행 수, 결측, 중복, 누락 분기, 코드 불일치, 실패한 호출). 상권 → 행정동 → 자치구 순으로 집계 가능한지 표시.
2. **블랙 검토** — 레드 산출물의 출처·단위·분기 일관성. 통과/반려를 `black_review.md`에.
3. **블루** — 성장 동인 MECE 트리 → 가설 5~8개 → 데이터로 검증 → Top N 후보와 베스트 프랙티스. `hypotheses.md` 표: 가설 / 검증 방법 / 결과 / 근거 데이터(파일·컬럼·분기) / 채택 여부.
4. **그린** — 블루 결과를 공격한다. raw 대비 가공값 표본 대조(최소 10건), 상권코드·행정동코드 혼용, 추정치·실측치 혼동, 생존편향·계절성·코로나 기저효과 같은 함정. `risks.md` (가드레일·병목·오류, 심각도 상·중·하).
5. **브라운** — 그린의 상·중 항목마다 데이터 기반 해결책. `solutions.md`. 해결 못 한 항목은 한계로 넘겨 보고서 '데이터 한계 및 보정 방법'에 싣는다.
6. **실버 + 블랙** — 베스트 솔루션 1개로 수렴: 입지(Top N 중 1순위와 근거) · 인테리어 컨셉 · 메뉴 포트폴리오(커피 중심) · 손익 시뮬레이션(가정 표기). `final_solution.md` + 실행 로드맵.
7. **옐로우** → `design_spec.md`, **오렌지** → `output/report.html`, **화이트** → `output/video/` (6~7은 옐로우 완료 후 오렌지·화이트 병렬).
8. **블랙 게이트** — `gate_check.py` + 출처 없는 수치 육안 확인. 하나라도 있으면 퍼플에 보내지 않고 반려.
9. **퍼플 1·2·3 병렬·독립 평가** — 서로의 점수를 보지 않는다. `scores_<회차>.json`.
10. **블랙 취합** — `iteration_log.md`에 회차, 항목별 점수(퍼플별), 수정 내용 기록. 통과면 종료.

**재작업.** 미달 항목에 책임 있는 에이전트만 다시 돌린다(전체 재실행 금지). 기본 매핑:

| 미달 항목 | 다시 돌릴 에이전트 |
|---|---|
| 정합성 | 레드 → 그린 → 브라운 → 오렌지 |
| 정교성 | 블루 → 그린 |
| 설득력 | 브라운 → 실버·블랙 → 오렌지 |
| 실행 시사점 | 실버·블랙 → 오렌지 |
| 전달력 | 옐로우 → 오렌지 → 화이트 |

재작업 에이전트에게는 직전 `scores_<회차>.json`의 감점 사유와 개선 요구를 그대로 넘긴다. **최대 5회.** 5회에도 미달이면 블랙이 최고점 회차 산출물을 최종본으로 지정하고, 미달 항목·사유·남은 개선 방향을 `iteration_log.md` 끝에 보고하고 종료한다.

## 출력 형식

`report.html` 목차(결론 우선):

1. 결론 한 장 — 1순위 상권, 매장 형태, 3년 손익 핵심 숫자
2. 상권 성장 동인 프레임워크 (MECE 트리)
3. 입지 선정 — 25개 자치구 → 행정동 → 상권 깔때기, Top N 비교표
4. 인테리어 컨셉 — 잠재 고객(시간대·연령·성별 매출 비중) 기반
5. 메뉴 구성 — 커피 중심 포트폴리오와 가격대
6. 손익 시뮬레이션 — 예상 매출·비용 구조·영업이익, 가정과 민감도
7. 예상 반론과 대응
8. **데이터 한계 및 보정 방법** (필수, 퍼플 설득용 핵심 섹션)
9. 실행 로드맵
10. 30초 영상 삽입 + 출처 목록(데이터셋명 / 기준 분기 / 호출일)

`scores_<회차>.json`:

```json
{"evaluator": "purple1", "round": 1,
 "scores": {"structure": 9.0, "analysis": 8.5, "argument": 9.0, "so_what": 9.5, "delivery": 9.0},
 "deductions": [{"item": "analysis", "reason": "…", "evidence": "report.html 3절 표 2", "fix": "…"}],
 "pass": false}
```

## 하지 말 것 (Guardrail)

- **출처 없는 숫자.** 모든 수치에 데이터셋명 / 기준 분기 / 호출일. 웹 근거면 URL. 계산값이면 계산식.
- **추정치를 실측처럼.** 추정매출은 카드 결제 기반 추정이다(현금·간편결제 일부 누락). 손익은 가정이다. 표기로 구분한다.
- **단위·분기 혼합.** 원/분기, 명/일처럼 통일하고, 비교하는 값은 같은 분기 기준.
- **코드 혼용.** 상권코드(TRDAR_CD)와 행정동코드(ADSTRD_CD)를 한 표에서 섞지 않는다.
- **API 키 노출.** 키는 환경변수나 `.env`에서만 읽고, 산출물·로그·대화 어디에도 적지 않는다.
- **범위 이탈.** 서울 밖, 커피 외 업종(베이커리 포함)으로 넓히지 않는다.
- **퍼플1을 실제 인물의 평가처럼.** 항상 "강정구님 관점을 참고한 평가 페르소나"로 표기한다.
- **점수 맞추기.** 퍼플은 통과시키려고 점수를 올리지 않는다. 9.5점은 "그대로 클라이언트 임원회의에 올릴 수 있다"는 뜻이다.
